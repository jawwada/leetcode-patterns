User asked (Oct 2026) to be taught DSA atomic operations by being quizzed directly in chat, chess-style: one small MCQ at a time via AskUserQuestion, levels 1-3 with points (10/20/30, +5 streak), missed concepts re-asked later in a different guise until answered right twice, topics mixed randomly, no dynamic programming. They rejected a plan to build a standalone drill web app; they want the interaction itself.

**Why:** They have a 20-year-old algorithms background and want to internalize mechanics, not read; a wrong answer with only "the answer is X" did not land.

**Source of truth:** the full rules now live in the user skill `.claude/skills/dsa-quiz/SKILL.md` in the Leetcode repo (symlinked from ~/.claude/skills/dsa-quiz) (invoke `/dsa-quiz`); update the skill, not just this memory, when the user adds a quiz rule ("add this to the skill").

**How to apply:** For every incorrect answer give three things: the correct answer, a COMPLETE worked example with visuals, and the intuition (the mental picture). The user said on 2026-10-04 "why do you show the summary after wrong answer, show complete example with visuals": do not compress the trace into a few lines or substitute a rule for it. Draw the data structure after every step (stack as a vertical column, linked list with arrows, heap as a tree and as an array, queue contents, dict contents), label each step with the operation and the decision taken, and show the final state. Summaries and rules come after the full picture, not instead of it. Define any term the user asks about (e.g. deque vs dequeue, monotonic stack) with a tiny trace before re-asking. Keep a running score and a revisit list in each reply. **Randomize the position of the correct option** (the user noticed on 2026-10-04 that the correct answer was almost always option A); pick the slot deliberately, roughly a quarter each for A, B, C, D, and never let the correct option be the longest or most detailed one. **Show the code in the question** (user, 2026-10-05: "you are already assuming that I know the code by heart, if you ask about code, you should print it there"): any question that asks what a loop, function or snippet does or produces must include that snippet verbatim in the question text; never assume the user remembers an algorithm's code. **Every problem-based question must state the problem first** (user, 2026-10-06: "you need to explain the problem and inputs/outputs with the code"): before the code, give a one-line problem statement, the input (types and a concrete example) and the expected output for that example, with a small sketch when the problem is visual. Never name a LeetCode problem and assume the user knows it. **Target the core challenge, not surface details** (user, 2026-10-06: "practise on the intuitive layer between the data structure, algorithms and code ... the problems should identify the core challenges and practise there, not superficial, really important"): each question picks the one non-obvious fact that makes the solution work (the invariant, the monotonic property, why an element can be discarded forever, why a commit is final) and asks the "why" that ties the data structure, the algorithm and one specific marked line of code together. Freeze a concrete moment in the run when that helps. Avoid trivia such as complexity recall, API names or syntax. **Topic distribution** (user, 2026-10-06), per 40-question cycle: strings 6, graphs 6, min-heap 6, trees 6 (15% each); backtracking 4, system design 4 (10% each); the remaining 8 slots: dynamic programming 2 (user asked for "a couple", an explicit exception to the no-DP rule for this quiz), and 1 each for two pointers / sliding window, binary search on answer, monotonic stack, prefix sums / hashing, intervals / greedy, linked list. Pick the next topic from whichever category is furthest below its quota; a problem spanning two categories counts for the primary one. System design questions follow the same core-challenge rule (the one constraint that forces the design choice) and still give scenario, numbers and expected outcome. When they say a question is unclear twice, park it and move on without a blocking clarification round. See [[google-interview-prep]].
